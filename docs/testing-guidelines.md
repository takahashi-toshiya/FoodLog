# テスト方針

この文書は、FoodLogで自動テストを書く目的と対象を定める。テスト件数やカバレッジ率を増やすことではなく、機能追加や変更によるバグを早く検知することを目的とする。

## 基本方針

- テストの分類名より、何が壊れたときに検知できるかを重視する
- 実装の内部構造ではなく、ビジネスルールと利用者から見える振る舞いを検証する
- 将来の変更で壊れやすく、人が毎回確認するのが難しい箇所を優先する
- 同じ振る舞いを複数の階層で重複してテストしない
- 単純な表示部品まで機械的にテストしない
- テスト件数やカバレッジ率そのものを目標にしない
- 発生した不具合は、可能な限り再現テストを追加してから修正する

## テストの構成

```text
tests/
└── meals/
    ├── services/     # ビジネスロジック
    ├── screens/      # 画面の主要な状態と操作
    └── storage/      # DBの保存・読み出し（導入後）
```

原則として、テストのディレクトリは `src/` の機能構成に対応させる。

## サービステスト

`services/` のテストでは、FoodLog固有の計算、検証、分類などのビジネスロジックを詳しく検証する。

対象例：

- PFCからのカロリー計算
- 1日分のカロリーとPFCの集計
- 目標値との差分や進捗率
- 食事入力のバリデーション
- 食事区分ごとの分類
- 体重変化や消費カロリーの推定

基本的なテスト観点：

- 正常な入力
- 空データ
- 0
- 負数や不正値
- 上限・下限
- 日付の境界

サービステストはReact Nativeの画面やDBへ依存させず、高速かつ決定的に実行できるようにする。

## スクリーンテスト

`screens/` のテストでは、画面内の複数コンポーネントを組み合わせ、重要な利用者操作と画面状態を検証する。

今日画面の対象例：

- 初期状態で選択日の記録が表示される
- 日付を選択すると、その日のデータへ切り替わる
- 記録がない日には空状態が表示される
- 集計結果が画面へ反映される
- 将来DBを接続した際に、読み込み中やエラー状態が適切に表示される

スクリーンテストでは、主要な利用者シナリオを代表するデータで確認する。サービスですでに検証している計算の全境界値を、画面テストで繰り返さない。

## コンポーネント単独のテスト

すべてのコンポーネントに単独テストを書く必要はない。次のいずれかに該当する場合に検討する。

- 複数画面で再利用される
- 独立した複雑な操作や状態を持つ
- アクセシビリティ上、個別に保証すべき振る舞いがある
- スクリーンテストだけでは異常系を検証しにくい

料理名やカロリーを表示するだけの行など、単純な表示コンポーネントはスクリーンテストで確認し、個別テストを増やさない。

## ストレージテスト

SQLiteなどのローカルDBを導入した時点で `storage/` のテストを追加する。可能な限り実際の保存処理を動かし、次を検証する。

- データを保存できる
- 保存したデータを読み出せる
- 日付やIDで正しく取得できる
- 編集内容が反映される
- 削除できる
- 日付をまたいでデータが混ざらない
- スキーマとアプリの型を正しく変換できる

SQLやスキーマの問題を検知する必要があるため、モックだけで完結させない。

## E2Eテスト

主要機能が揃ってから導入を検討する。実行時間と保守コストが高いため、アプリの価値に直結する少数の利用者導線に限定する。

対象例：

```text
食事追加を開く
→ 料理名とPFCを入力する
→ 保存する
→ 今日画面に表示される
→ カロリーとPFCの集計が更新される
```

E2Eテストのツールは、必要になった時点でExpoとReact Nativeの互換性を確認して選定する。

## 手動確認

自動テストだけでは、見た目や使用感を十分に保証できない。UI変更はExpo Goを使い、実機で次を確認する。

- 色、余白、文字サイズ
- 文字切れやレイアウト崩れ
- スクロールとタップの操作感
- セーフエリアとの重なり
- iOSとAndroidの表示差
- プロトタイプとの情報の優先順位

## 原則として書かないテスト

- 色、余白、角丸などを固定値で検証するテスト
- 全文言や全fixtureを列挙するだけのテスト
- コンポーネント数や使用Hookなど、内部構造を検証するテスト
- 同じ振る舞いをサービス、画面、E2Eのすべてで重複確認するテスト
- 大量のスナップショットテスト
- 実際のバグ検知につながらない、カバレッジ率だけを上げるテスト

## 機能開発時の判断手順

実装計画を作る際に、次の順番でテスト対象を決める。

1. 今回の変更で発生しそうなバグを挙げる
2. ビジネスルールはサービステストへ追加する
3. 重要な利用者操作と画面状態はスクリーンテストへ追加する
4. DBやAPIとの境界があれば、その接続を実際に動かすテストを検討する
5. 単純な表示部品は個別テストを作らない
6. 見た目と操作感は実機で確認する

実装後は、少なくとも次を実行する。

```bash
make test
```

機能全体の完了確認では、Lint、型チェック、ビルドも実行する。

```bash
make lint
make typecheck
make test
make build
```

## 方針の更新

テストが頻繁に壊れる、実際の不具合を検知できない、保守負担が大きい場合は、テストを増やす前に対象と粒度を見直す。実装を通して有効性が確認できたルールは、この文書へ反映する。
