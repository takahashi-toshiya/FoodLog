# 選択日の体重記録 実装計画

## 目的

Today画面で「食事」と「体重」を切り替え、選択した日の体重を手動で登録・確認・編集できるようにする。

## 実装範囲

- Today画面の日付選択欄の下に「食事」「体重」の切り替えを追加する
- タブはタップだけで切り替え、初期表示は「食事」とする
- 選択日ごとに体重を1件保存する
- 未記録の場合は新規登録し、記録済みの場合は同じ日付の記録を編集する
- 体重はkg単位の0より大きい数値として入力する
- 体重記録をSQLiteへ保存する
- 既存の食事表示、日付選択、食事追加・編集を維持する
- 要件定義、DB設計、ディレクトリ構成を実装内容に合わせて更新する

## 対象外

- 横スワイプによる日付変更
- タブのスワイプ切り替え
- 運動タブ
- 体重記録の削除
- 1日への複数回の体重記録
- 体重推移のグラフ、増減値、平均値の表示
- 目標体重の設定
- HealthKitや外部APIとの連携
- CSV出力

## 仕様

### Today画面の切り替え

- 日付ヘッダーと既存の日付選択欄は、食事と体重で共通とする
- 日付選択欄の下に「食事」「体重」のセグメントを表示する
- セグメントをタップすると、選択日を維持したまま表示内容を切り替える
- 日付を変更しても、選択中のセグメントは維持する
- 「食事」では既存の栄養サマリー、食事一覧、食事追加ボタンを表示する
- 「体重」では選択日の体重だけを表示し、食事追加ボタンは表示しない
- 読み込み中、未記録、取得失敗を体重側で区別して表示する
- 体重の取得失敗によって、食事タブを操作できない状態にしない

### 体重の登録・編集

- 未記録の場合は「未記録」と登録導線を表示する
- 記録済みの場合は体重をkg表記で表示し、編集導線を表示する
- 登録と編集には同じ入力UIを使用する
- 入力欄には記録済みの値を初期表示する
- 小数を入力でき、保存時に数値へ変換する
- 未入力、数値以外、0以下の値は保存しない
- 保存中は重複操作を防ぐ
- 保存に失敗した場合は入力内容を維持し、再試行できるようにする
- 保存成功後は入力UIを閉じ、選択日の保存値を再表示する

## データベース

`weight_records`テーブルを追加し、体重を日付単位で保存する。

```sql
CREATE TABLE weight_records (
  id TEXT PRIMARY KEY NOT NULL,
  recorded_date TEXT NOT NULL UNIQUE,
  weight_kg REAL NOT NULL CHECK (weight_kg > 0),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

- `recorded_date`は端末のローカル日付を`YYYY-MM-DD`形式で保存する
- `UNIQUE`制約によって同じ日付への複数登録を防ぐ
- 記録済みの日付へ保存した場合は、既存レコードの`id`と`created_at`を維持して体重と`updated_at`を更新する
- スキーマバージョンを`4`へ更新し、既存データを維持したままテーブルを追加する

## 実装方針

### 画面の責務

Today画面は、選択日と表示中のセグメントを管理し、食事と体重の表示を組み立てる。Today画面が食事機能だけに属する状態を解消するため、画面本体は`today/`へ移し、食事固有の表示や処理は引き続き`meals/`に置く。

体重の入力UIにはSQLiteを直接扱わせない。画面がRepositoryを通じて取得・保存し、入力UIは値の入力、エラー表示、保存イベントの通知を担当する。

### 保存処理

`WeightRepository`を保存境界とし、`SQLiteWeightRepository`で次の操作を実装する。

- 日付による体重記録の取得
- 日付単位での体重記録の新規登録または更新

入力値の検証と数値変換は`weights/services/`へ置き、画面やSQLiteへ依存させない。

## 起こりそうな失敗

- 食事と体重を切り替えた際に選択日が今日へ戻る
- 日付を変更した際に、変更前の日付の体重が一瞬表示される
- 同じ日付の編集で別レコードが追加される
- 文字列や0以下の値が保存される
- 小数の変換で体重が意図せず丸められる
- 保存の連続操作で同じ日付の登録が競合する
- 体重の読み込み失敗によって食事まで表示できなくなる
- 体重タブでも食事追加ボタンが表示される
- Today画面の移動によって既存の食事表示や遷移が壊れる
- マイグレーションによって既存の食事、食品、目標値、セットが失われる

## テスト計画

### 入力検証

- 正の整数と小数を体重として受け付ける
- 未入力、数値以外、0、負数を拒否する
- 入力した小数を意図せず整数へ丸めない

### ストレージ

- 選択日に体重を保存し、同じ日付で取得できる
- 未記録の日付では`null`を返す
- 記録済みの日付へ保存すると新規追加せず既存値を更新する
- 更新時に`id`と`created_at`を維持し、`updated_at`を更新する
- 同じ日付への重複をDB制約でも防止できる
- スキーマバージョン3から4へ移行し、既存データを維持できる

### 画面

- 初期表示では食事タブが選択され、既存の食事内容を表示する
- 体重タブを押すと、同じ選択日の体重表示へ切り替わる
- 日付を変更しても体重タブを維持し、変更後の日付の値を表示する
- 未記録の日付では未記録状態と登録導線を表示する
- 正しい値を保存すると、選択日の体重として表示する
- 記録済みの値を編集すると、表示値を更新する
- 不正な入力では保存処理を呼び出さず、入力エラーを表示する
- 保存失敗時は入力内容を維持する
- 体重タブでは食事追加ボタンを表示しない
- 体重の取得失敗後に再試行でき、食事タブは引き続き利用できる
- Today画面の移動後も、既存の日付選択、食事追加、食事編集が動作する

### 手動確認

- Expo Goで食事と体重をタップして切り替えられる
- 複数の日付へ体重を登録し、日付ごとに異なる値が表示される
- 記録済みの値を編集できる
- 小数キーボードで入力でき、キーボード表示中も保存操作ができる
- iOSとAndroidで入力UI、キーボード、レイアウトに問題がない
- アプリを再起動しても保存した体重が残る

## 実装段階

### 第1段階：DB・Repository

- 要件定義とDB設計へ体重記録を追加する
- スキーマバージョン4のマイグレーションを実装する
- 体重の型、Repository、SQLite実装を追加する
- 入力検証とストレージのテストを追加する

この段階では、データ構造と保存処理が日付ごとの体重記録を正しく扱えることを確認する。

### 第2段階：Today画面と体重入力

- Today画面を`today/`へ移す
- 「食事」「体重」のセグメントを追加する
- 体重の未記録、表示、登録、編集、読み込み、エラー状態を実装する
- Today画面と既存食事機能のテストを更新する
- 関連する構成資料を更新する

この段階では、利用者が選択日の体重を登録・確認・編集でき、既存の食事操作が維持されていることを確認する。

## 完了条件

- Today画面で食事と体重をタップして切り替えられる
- 選択日ごとに体重を1件登録・確認・編集できる
- 不正な値や同じ日付への重複レコードを保存しない
- 体重の状態やエラーが既存の食事機能へ影響しない
- 既存データと既存の食事操作が維持される
- Format、Lint、型チェック、テスト、ビルドが成功する
- Expo Goの実機確認で主要操作に問題がない
