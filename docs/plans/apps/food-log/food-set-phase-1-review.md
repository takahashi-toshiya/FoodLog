# 食品セット 第1段階レビュー用メモ

このファイルは、食品セット機能の第1段階「DB・Repository」の実装意図を伝えるための一時的なレビュー資料である。

## 今回実装した範囲

- `food_sets`と`food_set_items`の追加
- スキーマバージョン3へのマイグレーション
- 食品セットの型定義
- `FoodSetRepository`とSQLite実装
- 保存処理とマイグレーションのテスト

画面、入力検証、食事への一括追加はまだ実装していない。

## 実装意図

### `food_set_items`を中間テーブルにした理由

同じライブラリ食品を複数のセットで再利用しつつ、セットごとの摂取倍率と表示順を持たせるため。食品の栄養情報は複製せず、`foods`を参照する。

### Repositoryの取得結果に食品情報を含めた理由

画面側で食品IDごとに追加取得しなくてよいよう、`food_sets`、`food_set_items`、`foods`をJOINし、`FoodSet`の中に`FoodItem`を含めて返す。SQLの複数行は`mapFoodSetRows`でセット単位に組み立て直している。

この構造では、ライブラリ食品を編集すると、次回取得時のセット表示と今後の食事追加には新しい値が使われる。過去の食事記録は値を複製して保存するため変わらない。

### 登録・更新をトランザクション化した理由

セット本体と項目の一部だけが保存される状態を防ぐため。いずれかの保存に失敗した場合は、変更全体を取り消す前提にしている。

### 更新時に項目を入れ直す理由

食品の追加・削除・倍率・表示順を個別に差分更新するより、現在の入力内容を正として既存項目を削除し、同じトランザクション内で再登録する方が処理を単純に保てるため。

### 食品削除を`RESTRICT`にした理由

ライブラリ食品を削除した結果、利用者が知らない間にセット内容まで変わることを防ぐため。セットから食品を外した後でなければ、その食品を削除できない。

### セット削除を`CASCADE`にした理由

セットを削除したとき、そのセットだけで使用する中間テーブルの項目を残す意味がないため。親セットの削除と同時に項目も削除する。

### `sort_order`を保存した理由

取得のたびに食品の順序が変わらないようにするため。入力配列の順番を0始まりで保存し、取得時もこの値で並べる。

### 保存後にDBから取得し直す理由

登録・更新の戻り値を画面側で組み立てず、JOINや変換を含めた通常の取得結果と同じ形式で返すため。保存できたはずのセットが取得できない場合は、`findRequired`で異常として扱う。

## 特に伝わりにくそうな箇所

- `mapFoodSetRows`は、JOINによって食品数分に増えた行を1つの`FoodSet`へ戻す処理
- `INNER JOIN`を使っているため、食品が0件のセットは取得結果に現れない。Repository側でも0件での登録・更新を拒否している
- `(food_set_id, food_id)`の一意制約により、同じ食品を同一セットへ重複登録できない
- `food_set_items_food_id_index`は、食品削除時などにその食品を参照するセット項目を探しやすくするためのもの

## テストで確認している範囲

- JOIN結果をセット単位へ変換できること
- 項目の表示順を維持できること
- 登録と更新でトランザクションAPIを使用すること
- 更新時に既存項目を削除して再登録すること
- 空のセットと存在しないセットを拒否すること
- マイグレーションに外部キー、一意制約、スキーマバージョン3が含まれること

RepositoryテストではSQLite APIをモックしているため、SQLite実体でのロールバックや制約動作そのものまでは検証していない。
