# ライブラリ食品の編集・削除 実装計画

## 目的

ライブラリに登録した食品の内容を変更または削除できるようにし、よく使う食品を利用者自身で管理できる状態にする。

## 参照資料

- 要件：`docs/requirements.md`
- DB設計：`docs/database-design.md`
- コーディング規約：`docs/coding-guidelines.md`
- ディレクトリ構成：`docs/project-structure.md`
- テスト方針：`docs/testing-guidelines.md`
- 既存実装：食品登録画面、ライブラリ画面、FoodRepository

## 実装範囲

- 食品カードのメニューボタンから編集・削除操作を選択できるようにする
- 保存済みの食品をIDで取得し、編集画面へ初期表示する
- 食品名、1回分の量・単位、PFC、カロリー、メモを編集できるようにする
- 編集内容を検証してSQLiteへ保存する
- 削除前に確認ダイアログを表示し、承認後にSQLiteから削除する
- 編集または削除の完了後、ライブラリ画面の食品一覧を再取得する
- 食品登録画面と編集画面で入力フォームと検証処理を共通利用する

## 利用者の流れ

### 編集

```text
ライブラリで食品カードのメニューを押す
↓
「編集」を選択する
↓
編集画面に現在の内容を表示する
↓
内容を変更して保存する
↓
ライブラリへ戻り、更新後の食品を表示する
```

### 削除

```text
ライブラリで食品カードのメニューを押す
↓
「削除」を選択する
↓
削除確認を表示する
↓
削除を承認する
↓
ライブラリから対象食品を除外する
```

## 仕様

### 食品カードの操作

- 食品カード本体を押した場合は、現在どおり食事追加画面へ進む
- カード右端のメニューボタンを押した場合は、食品を選択する処理を実行しない
- メニューには「編集」「削除」「キャンセル」を表示する
- メニューのタイトルには食品名、説明には「この食品の操作を選択してください」を表示する
- 「編集」は対象食品IDを渡して編集モーダルを開く
- 「削除」は確認ダイアログを表示し、承認された場合だけ削除する

### 編集

- 入力項目と検証ルールは食品登録画面と同じにする
- 更新時は`id`と`createdAt`を維持し、`updatedAt`を更新する
- `foods`にはカロリーの入力方法を保存していないため、保存値がPFC計算値と一致する場合は自動計算、一致しない場合は手動入力として初期表示する
- 保存中は再度保存できないようにする
- 保存成功後は編集画面を閉じ、ライブラリの一覧を再取得する

### 削除

- 削除確認には対象の食品名を表示する
- 削除確認には「過去の食事記録は削除されません。」と表示する
- キャンセルした場合は何も変更しない
- 削除処理中は同じ操作を重複実行しない
- 削除成功後はライブラリの一覧を再取得する
- 食品を削除しても、過去に保存した食事記録の名称・カロリー・PFCは変更または削除しない
- 削除された食品を参照していた`meal_entries.source_food_id`は、既存の外部キー制約により`null`へ変更する

### 読み込み・エラー

- 編集対象の取得中は、空の入力フォームを一瞬表示せず読み込み状態にする
- 指定IDの食品が存在しない場合は編集フォームを表示せず、閉じられるエラー状態にする
- 取得、更新、削除に失敗した場合は、処理に対応したエラーを表示する
- 更新失敗時は入力内容と編集画面を維持する
- 削除失敗時は食品を一覧から消さず、再試行できる状態を維持する
- SQLiteの内部エラーは利用者へ直接表示しない

## 実装方針

### フォームの共通化

食品登録と編集で同じ入力項目が必要になるため、共通の食品入力フォームを作る。

- 共通フォーム：入力状態、入力エラー、PFCによるカロリー表示、入力UIを担当する
- 食品登録画面：新規登録用の初期値と作成処理を担当する
- 食品編集画面：既存食品の取得、編集用初期値、更新処理を担当する
- Repositoryの呼び出しや画面遷移を共通フォームへ持ち込まない

既存の食品登録画面の見た目と動作は、共通化によって変更しない。

### Repository

`FoodRepository`へ次の操作を追加する。

- 既存食品の更新
- IDによる削除

IDによる1件取得は既存の`findById`を使用する。`SQLiteFoodRepository`で更新・削除SQLを実装し、画面からSQLite APIやSQLを直接呼び出さない。

複数ファイルで共有している食品保存用の入力型は、型配置ルールに従って`foods/types/`へ移す。

### DB

既存の`foods`テーブルと`meal_entries`の外部キー制約で対応できるため、スキーマ変更とマイグレーション追加は行わない。

## 起こりそうな失敗

- メニューボタンを押した際に、カード本体の食事追加処理も実行される
- 編集画面に保存済みの値が正しく復元されない
- 手動入力したカロリーが、編集画面を開いただけでPFC計算値へ変わる
- 更新によって`id`や`createdAt`が変わる
- 削除確認をキャンセルしても食品が削除される
- 保存や削除の連打で処理が重複する
- 食品削除によって過去の食事記録まで削除される
- 更新・削除後も古い食品一覧が表示される
- フォーム共通化によって既存の食品登録機能が壊れる

## テスト計画

### ライブラリ画面

- 食品カード本体を押した場合は、これまでどおり食事追加導線を呼び出す
- メニューボタンを押した場合は、カード本体の処理を呼び出さない
- メニューから編集を選ぶと、対象食品IDを編集導線へ渡す
- 削除をキャンセルした場合はRepositoryの削除処理を呼び出さない
- 削除を承認した場合だけ対象IDを削除する
- 削除成功後に食品一覧を再取得する
- 削除失敗時は対象食品と画面を維持する

### 食品編集画面

- 保存済みの食品情報を初期表示する
- PFC計算値と保存カロリーが一致する場合は自動計算として表示する
- PFC計算値と保存カロリーが異なる場合は手動カロリーとして表示する
- 編集した値でRepositoryの更新処理を呼び出す
- 不正な入力では更新処理を呼び出さない
- 更新成功後に編集画面を閉じる
- 更新失敗時は入力内容と編集画面を維持する
- 対象IDが存在しない場合はエラー状態を表示する
- 保存中の連続操作で更新が重複しない

### ストレージ

- 食品を更新できる
- 更新後も`id`と`createdAt`を維持し、内容と`updatedAt`を更新できる
- 食品を削除できる
- 存在しないIDの更新・削除を成功扱いにしない
- 食品削除後も過去の食事記録が残り、`source_food_id`だけが`null`になる

### 既存テスト

- 食品入力の検証テストを維持する
- 食品登録画面の保存テストを維持し、共通化による回帰を検知する
- ライブラリの検索・選択・空状態のテストを維持する
- ライブラリ食品から食事を追加するテストを維持する

### 手動確認

- 食品カード本体とメニューボタンが別々に操作できる
- 各入力値を編集して保存すると、ライブラリへ反映される
- 自動計算と手動カロリーの食品をそれぞれ編集できる
- 削除確認のキャンセルと削除をそれぞれ確認する
- 食品を削除しても、過去の食事記録の表示と集計が変わらない
- iOSとAndroidでモーダル、キーボード、スクロール、確認ダイアログを確認する

## 完了条件

- ライブラリ食品を編集・削除できる
- 編集・削除後にライブラリの一覧へ結果が反映される
- 食品カード本体の既存の食事追加導線が維持される
- 食品を削除しても過去の食事記録が維持される
- 取得・更新・削除の失敗時にデータや入力内容を失わない
- 追加したテストと既存テストが成功する
- Format、Lint、型チェック、テスト、ビルドが成功する
- Expo Goの実機確認で主要操作に問題がない
