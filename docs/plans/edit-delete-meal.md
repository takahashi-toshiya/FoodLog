# 食事記録の編集・削除 実装計画

## 目的

Today画面に保存済みの食事記録を開き、内容の編集または削除ができるようにする。

## 参照資料

- 要件：`docs/requirements.md`
- DB設計：`docs/database-design.md`
- コーディング規約：`docs/coding-guidelines.md`
- ディレクトリ構成：`docs/project-structure.md`
- テスト方針：`docs/testing-guidelines.md`
- 既存実装：食事追加画面、Today画面、MealRepository

## 実装範囲

- Today画面の食事記録を押すと、編集画面をモーダルで開く
- 保存済みの食事記録をIDで取得し、入力欄の初期値にする
- 日付、食事区分、食品・料理名、PFC、摂取倍率、カロリー入力方法、メモを編集できる
- 編集内容を検証してSQLiteへ保存する
- 削除前に確認ダイアログを表示し、承認後にSQLiteから削除する
- 編集または削除の完了後、Today画面の一覧と栄養集計を再取得する
- 食事追加画面と編集画面で、入力フォームと検証処理を共通利用する

## 利用者の流れ

### 編集

```text
Today画面で食事記録を押す
↓
編集画面に現在の内容を表示
↓
内容を変更して保存
↓
Today画面へ戻り、保存後の日付の記録と集計を表示
```

### 削除

```text
編集画面で「削除」を押す
↓
確認ダイアログを表示
↓
削除を承認
↓
Today画面へ戻り、元の日付の記録と集計を更新
```

## 仕様

### 編集画面への遷移

- Today画面の食事記録1件をタップ可能にする
- 編集対象はルートパラメータの食事記録IDで指定する
- 編集画面は下部タブに追加せず、モーダルルートとして扱う

### 編集

- 入力項目と検証ルールは食事追加画面と同じにする
- 更新時は`id`と`createdAt`を維持し、`updatedAt`を更新する
- ライブラリから追加した食事でも、編集対象は食事記録のスナップショットだけとする
- 元の`foods`レコードは変更せず、`sourceFoodId`は由来を示す値として維持する
- 日付を変更した場合、保存後は変更先の日付をToday画面で表示する
- 保存処理中は再度保存または削除できないようにする

### 削除

- 削除操作は編集画面に配置する
- 確認ダイアログにはキャンセルと削除を表示する
- キャンセルした場合は何も変更しない
- 削除処理中は保存および削除の重複操作を防ぐ
- 削除後は編集前の日付へ戻り、Today画面を再取得する
- 食事記録を削除しても、参照元の`foods`レコードは削除しない

### 読み込み・エラー

- 食事記録の取得中は、空の入力フォームを一瞬表示せず読み込み状態にする
- 指定IDの記録が存在しない場合は編集フォームを表示せず、戻れるエラー状態にする
- 取得、更新、削除に失敗した場合は編集画面を閉じない
- 更新または削除の失敗後も入力内容を維持し、再試行できるようにする
- SQLiteの内部エラーは利用者へ直接表示しない

## 実装方針

### フォームの共通化

食事追加と編集で同じ入力項目と操作が必要になるため、共通の食事入力フォームを作る。

- 共通フォーム：入力状態、入力エラー、PFC・摂取倍率による表示計算、入力UIを担当する
- 食事追加画面：初期値の作成と新規保存を担当する
- 食事編集画面：既存データの取得、更新、削除を担当する
- Repositoryの呼び出しや削除確認を共通フォームへ持ち込まない

既存の食事追加画面の見た目と挙動は、共通化によって変更しない。

### Repository

`MealRepository`へ次の操作を追加する。

- IDによる1件取得
- 既存の食事記録の更新
- IDによる削除

`SQLiteMealRepository`で対応するSQLを実装する。画面からSQLite APIやSQLを直接呼び出さない。

### DB

既存の`meal_entries`テーブルで必要な情報を保持できるため、スキーマ変更とマイグレーション追加は行わない。

## 起こりそうな失敗

- 編集画面に保存済みの値が正しく復元されない
- 摂取倍率を二重に適用し、PFCやカロリーが変化する
- 編集時に参照元のライブラリ食品まで変更する
- 日付変更後も変更前の日付を表示し、更新結果が見えない
- 削除確認のキャンセルでも削除処理が実行される
- 保存や削除の連打で処理が重複する
- 取得や保存の失敗時に、入力内容を失ったまま画面が閉じる
- フォーム共通化によって既存の食事追加機能が壊れる

## テスト計画

### スクリーンテスト

- Today画面で食事記録を押すと、対象IDを編集導線へ渡す
- 編集画面に保存済みの値が初期表示される
- 編集した値でRepositoryの更新処理を呼び出す
- 摂取倍率を変更した場合、PFCとカロリーが正しく計算されて保存される
- 更新成功後、保存後の日付をToday画面へ渡す
- 更新失敗時は入力内容と編集画面を維持する
- 削除確認をキャンセルした場合は削除しない
- 削除を承認した場合だけRepositoryの削除処理を呼び出す
- 削除失敗時は編集画面を維持する
- 対象IDが存在しない場合はエラー状態を表示する
- 処理中の連続操作で更新や削除が重複しない

### ストレージテスト

- IDで食事記録を1件取得できる
- 存在しないIDでは`null`を返す
- 更新後も`id`と`createdAt`を維持し、内容と`updatedAt`を更新できる
- 日付と食事区分を含む全編集項目を正しく更新できる
- 食事記録を削除できる
- 削除後も参照元の食品が残る
- 存在しないIDの更新・削除を成功扱いにしない

### 既存テスト

- 食事入力の検証テストを維持する
- 食事追加画面の保存テストを維持し、共通化による回帰を検知する
- Today画面の一覧・栄養集計テストを維持する

### 手動確認

- Today画面から対象の食事記録を開ける
- 各入力値を編集して保存すると、一覧と集計へ反映される
- 日付を変更すると、変更先の日付に記録が表示される
- ライブラリ由来の食事を編集しても、ライブラリの食品は変わらない
- 削除確認のキャンセルと削除をそれぞれ確認する
- iOSとAndroidでモーダル、キーボード、スクロール、確認ダイアログを確認する

## 完了条件

- 保存済みの食事記録をToday画面から編集・削除できる
- 編集・削除後にToday画面の一覧と栄養集計が正しく更新される
- 食事記録の編集がライブラリ食品へ影響しない
- 取得・更新・削除の失敗時にデータや入力内容を失わない
- 追加したテストと既存テストが成功する
- Lint、型チェック、テスト、ビルドが成功する
- Expo Goの実機確認で主要操作に問題がない
