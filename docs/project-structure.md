# ディレクトリ構成

この文書は、FoodLogのコードをどこへ配置し、各領域が何を担当するかを定める。

## 基本方針

- アプリケーションコードは `src/` に置く
- `src/` は技術の種類ではなく、食事や設定などの機能を中心に分ける
- Expo Routerのルートファイルは薄く保ち、画面の本体を機能ディレクトリへ置く
- 機能だけで使用するコードは、その機能内に置く
- 複数の機能から実際に使われるコードだけを `shared/` へ移す
- ブラウザ版の `prototype/` はUI参照用であり、本番アプリからimportしない

## 想定構成

```text
FoodLog/
├── assets/                  # 画像、アイコン、フォントなどの静的ファイル
├── docs/                    # 要件、技術方針、規約、実装計画
│   └── plans/               # 機能単位の実装計画
├── prototype/               # ブラウザ版UIプロトタイプ
├── src/
│   ├── app/                 # Expo Routerのルート定義
│   ├── meals/               # 食事記録機能
│   │   ├── components/      # 食事機能内の表示コンポーネント
│   │   ├── screens/         # 食事機能の画面本体
│   │   ├── types/           # 食事機能で共有する型定義
│   │   ├── constants/       # 食事区分などの固定値
│   │   ├── services/        # 食事機能固有のビジネスロジック
│   │   ├── storage/         # 食事データの保存境界と実装
│   │   └── fixtures/        # 開発・テスト用の仮データ
│   ├── foods/               # よく使う食品とセット機能
│   ├── settings/            # 目標値などの設定機能
│   └── shared/              # 複数機能で共有するコード
│       ├── components/      # 共通UI
│       ├── theme/           # 色、余白、文字スタイル
│       └── utils/           # 日付操作など、責務が明確な汎用処理
└── tests/                   # アプリコードに対応するテスト
```

必要になっていないディレクトリは先に作らない。上記は配置ルールであり、空ディレクトリを維持するためのものではない。

## 各領域の責務

### `src/app/`

- Expo Routerのルート、レイアウト、画面遷移を定義する
- URLやルートパラメータをアプリ内の画面へ渡す
- 大きなJSX、ビジネスロジック、データ保存処理を置かない

### 機能ディレクトリ

`meals/`、`foods/`、`settings/` のように、利用者から見た機能ごとにコードをまとめる。

- `components/`：その機能だけで使用する表示部品
- `screens/`：画面全体の状態と構成
- `types/`：その機能内で共有する型定義だけ
- `constants/`：固定の選択肢やラベル
- `services/`：計算、検証、分類などのビジネスロジック
- `storage/`：保存先に依存しないインターフェースと保存実装
- `fixtures/`：プロトタイプ確認用の仮データ

すべての機能が同じサブディレクトリを持つ必要はない。コードが増え、分類が必要になったものだけ作成する。

### `src/shared/`

- 2つ以上の機能から実際に利用されるコードを置く
- 将来使いそうという理由だけで機能固有のコードを移さない
- `utils/` のファイル名は、日付処理や数値表示など責務が分かる名前にする

### `types/`、`services/`、`shared/utils/` の境界

`types/` には型定義だけを置く。

- `MealEntry` や `MealType` など、その機能内で共有する型
- コンポーネント専用のProps型は含めず、利用するコンポーネントと同じファイルに置く

`services/` には、画面や保存先がなくてもFoodLogの機能として意味を持つ処理を置く。

- PFCとカロリーの計算
- 食事入力の検証
- 食事区分ごとの分類

API通信と端末内の保存処理は、それぞれ `api/` と `storage/` に置き、`services/` へ含めない。

`shared/utils/` には、FoodLog固有ではない汎用的な処理を置く。

- 日付の加減算
- 日付キーへの変換
- 日付や数値の表示整形

機能固有の処理を `shared/utils/` へ移さず、対応する機能の `services/` に置く。

### `tests/`

- 原則として `src/` の機能構成に対応させる
- 例：`src/meals/services/nutrition.ts` に対するテストは `tests/meals/services/nutrition.test.ts`
- フレームワーク上、実装の近くに置く方が明確な場合はコロケーションも認める

## 依存関係の方向

```text
src/app
  ↓
機能のscreens
  ↓
機能のcomponents / services / storage
  ↓
src/shared
```

- `shared/` から特定の機能へ依存しない
- `services/` から画面やReact NativeのUIへ依存しない
- 表示コンポーネントから具体的なDB実装を直接呼ばない
- 機能間でデータが必要な場合は、共有すべき責務を確認してから接続する

## データ保存の境界

ローカルDBを採用しても、画面やビジネスロジックがSQLite固有のAPIへ直接依存しない構成にする。

```text
画面・ユースケース
      ↓
保存インターフェース
      ↓
ローカルDB実装
```

将来クラウド同期を追加する場合も、保存インターフェースの利用側を大きく変更せず、実装の追加や切り替えで対応できることを目指す。

## 構成の変更

- 1ファイルが大きいという理由だけで機械的に分割しない
- 責務が複数ある、独立してテストしたい、複数箇所で使う場合に分割する
- 新しいトップレベル分類を追加する場合は、この文書も更新する
- 実装計画のファイル構成案は、この文書の方針に従う
