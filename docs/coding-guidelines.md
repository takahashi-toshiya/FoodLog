# コーディング規約

この文書は、FoodLogの実装で共通して守るコード上のルールを定める。実装を通して必要性が確認できたルールだけを追加し、過度に細かい規約にはしない。

## 基本方針

- TypeScriptのstrictモードを維持する
- 読みやすさと変更しやすさを、短さや抽象化より優先する
- 画面表示、状態管理、ビジネスロジック、データ保存の責務を分離する
- 将来の再利用を予想した抽象化は避け、実際に必要になった時点で共通化する
- 新しいライブラリは、標準機能や既存の依存関係で解決できない場合にのみ追加する
- 複雑な処理には「何をしているか」ではなく「なぜ必要か」をコメントする

## TypeScript

- `any` は原則使用しない。外部データなど型が不明な値には `unknown` を使い、検証してから利用する
- コンポーネントのProps、関数の引数、戻り値など、外部との境界には明示的な型を定義する
- 型アサーションによる問題の回避を常用しない
- `null` と `undefined` は用途を曖昧に混在させない
- ドメインを表す型には、`MealEntry` や `NutritionGoal` のような具体的な名前を付ける
- 複数箇所で共有しない型は、利用するファイルの近くに置く

## 型・サービス・ユーティリティ

- 機能固有の共有型は、その機能の `types/` に置く
- `types/` には型定義だけを置き、関数や定数を含めない
- `services/` には、画面や保存先が変わっても残るFoodLog固有の計算、検証、分類を置く
- API通信は `api/`、端末内の保存処理は `storage/` に置き、`services/` に混在させない
- 固定の選択肢やラベルは機能内の `constants/` に置く
- 日付操作や表示整形など、FoodLog固有ではない処理は `shared/utils/` に置く
- コンポーネント専用のProps型は、コンポーネントと同じファイルに置く
- APIやDBの形式だけを表す型は、それぞれ `api/`、`storage/` の近くに置く

## React Nativeコンポーネント

- 画面コンポーネントは、データ取得、画面状態、子コンポーネントの組み立てを担当する
- 表示コンポーネントは、可能な限りPropsから表示が決まる形にする
- カロリー計算や入力値検証などのビジネスロジックをJSX内に直接書かない
- コンポーネントは、独立した責務、複雑な表示、または実際の再利用性がある場合に切り出す
- 単純な装飾要素まで細かくコンポーネント化しない
- Propsをそのまま別のコンポーネントへ流すだけの中間コンポーネントを増やさない
- 状態は、それを必要とする最も近い共通の親に置く
- `useEffect` は外部システムとの同期に使用し、値の計算だけには使用しない
- リストの `key` に配列のindexを使用しない。安定したIDを使う

## Propsとイベント

- Propsの型名は原則として `<ComponentName>Props` とする
- 真偽値のPropsには `is`、`has`、`can`、`should` など、意味が分かる名前を使う
- イベントを受け取るPropsは `onSelectDate` や `onAddMeal` のように `on` から始める
- コンポーネント内のイベント処理関数は `handleSelectDate` のように `handle` から始める
- 画面固有の都合を、再利用する表示コンポーネントのPropsへ持ち込まない

## スタイリング

- React Nativeの `StyleSheet.create` を基本とする
- 色や余白など、複数箇所で実際に共有する値はテーマまたは共通定数へ集約する
- 固定の画面幅・高さを前提にしない
- iOSとAndroidのセーフエリアを考慮する
- タップ可能な要素には十分な操作領域を確保する
- 色だけに依存せず、文字や形でも状態を判別できるようにする
- WebプロトタイプのCSSをそのまま移植せず、React Nativeに適したレイアウトへ置き換える

## 命名とファイル

- ReactコンポーネントはPascalCaseで命名する
- 関数、変数、HookはcamelCaseで命名する
- 定数は、真に不変なモジュール定数に限りUPPER_SNAKE_CASEを使用する
- カスタムHookは `use` から始める
- テストファイルは対象名に合わせて `*.test.ts` または `*.test.tsx` とする
- `index.ts` による再エクスポートは、公開境界が明確になる場合だけ使用する
- `utils.ts`、`helpers.ts` のように責務が分からないファイルへ処理を集めない

## エラーと入力値

- ユーザー入力は保存前に検証する
- エラーを握りつぶさず、利用者向け表示と開発者向け情報を分けて扱う
- 想定可能な未入力や不正値を例外だけで制御しない
- 日付、数値、単位の変換処理は一箇所にまとめ、画面ごとに異なる解釈を持たせない

## テスト

- 詳細なテスト方針は `docs/testing-guidelines.md` に従う
- ビジネスロジックはUIから分離し、純粋関数として単体テストする
- 画面テストは内部実装ではなく、利用者が確認できる表示と操作を検証する
- 正常系に加え、空状態、不正入力、境界値、日付の切り替わりを検証する
- テスト内で現在時刻に依存する場合は時刻を固定する
- テストを通すためだけの本番コード分岐を追加しない
- 振る舞いを変更する実装には、対応するテストを追加または更新する

## 実装前後の確認

実装前に、対象機能の実装計画と関連ドキュメントを確認する。実装後は次を実行する。

```bash
make lint
make typecheck
make test
make build
```

UI変更はExpo Goでも確認する。

## 規約の更新

- 同じレビュー指摘が繰り返された場合は、この文書への追加を検討する
- 一度しか発生しない画面固有の仕様は、実装計画またはテストへ記載する
- 実態と合わなくなった規約は放置せず、コード変更と同じようにレビューして更新する
